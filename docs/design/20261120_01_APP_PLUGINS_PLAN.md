# Plugins contributed by the app itself

## 1. What it is

Today every `MobileActivityPlugin` an APK carries is one of libmobile's
own, listed in `codegen::PLUGINS` and chosen by Cargo features. An app
that needs a small piece of Android of its own (ShotToss's MediaStore
queries, for instance) can only subclass `MobileNativeActivity`, name the
subclass with `Project::activity`, and add its sources with a hand-written
`Project::extra_script`. This plan lets the app's `build.rs` say it in one
call:

```rust
libmobile::gradle::Project::new("dev.tmzt.shottoss")
    .plugin(
        AppPlugin::new("dev.tmzt.shottoss.media.MediaStorePlugin")
            .sources("android/java")
            .permission("android.permission.READ_MEDIA_IMAGES"),
    )
    .generate()?;
```

The plugin's Kotlin is compiled into the generated Gradle project and the
object is dispatched every lifecycle hook, exactly as libmobile's own
plugins are. Its `external fun`s are implemented in the app's own cdylib.

## 2. History: was it planned and dropped?

Searched: `git log --all --oneline -- '*plugin*'`, `git log --all -S` for
`AppPlugin`, `app_plugin`, `extra_plugin`, `add_plugin`,
`register_plugin` and "app plugins", every document in `docs/design/` and
`CHANGES.md`, here and in libmorph. There is **no earlier plan** for app
plugins, open or dropped, so nothing is to be consolidated or superseded
(Rule 1.8). The only earlier traces are:

- `AGENTS.md`'s project brief, which describes the compile-time registry
  for libmobile's own features only;
- `MobileNativeActivity.kt`'s doc comment since the first commit
  (`21938c4`), which shows the subclass route
  (`override val plugins = GeneratedPlugins.activePlugins + MyPlugin`).

That route stays. This plan adds the generated one beside it.

## 3. Decisions

### 3.1 Where the app's list lives: `GeneratedAppPlugins`

`GeneratedPlugins.kt` is written by **libmobile's** build script, into its
`OUT_DIR`, per feature set: every app built with the same features shares
that file, and it is written before the app's build script runs. The
app's plugins cannot go into it. They go into a second object, written by
the **app's** build script (`Project::generate`) into the generated Gradle
project:

```kotlin
// GENERATED by libmobile::gradle from the app's build.rs. Do not edit.
package dev.highbay.libmobile

object GeneratedAppPlugins {
    val plugins: List<MobileActivityPlugin> = listOf<MobileActivityPlugin>(
        dev.tmzt.shottoss.media.MediaStorePlugin,
    )
}
```

at `app/libmobile-app-plugins/dev/highbay/libmobile/GeneratedAppPlugins.kt`
under the project directory.

libmobile's build script also writes a default, empty
`GeneratedAppPlugins.kt` into its own `OUT_DIR/app-plugins/` (a separate
source root beside `OUT_DIR/java/`). `libmobile.gradle` adds that root,
unless the project property `LIBMOBILE_APP_PLUGINS_ROOT`
(`codegen::APP_PLUGINS_ROOT_PROPERTY`) is set, in which case it adds the
named root instead. The generated app module sets it, before applying
`libmobile.gradle`, only when the app has plugins. So:

- an app with no plugins gets a byte-identical generated project and an
  empty default list;
- a hand-written project keeps working unchanged (the default root), and
  may set the property itself to supply its own `GeneratedAppPlugins.kt`.

`GeneratedPlugins.kt` and `codegen::generated_plugins_kt` do not change.

### 3.2 Dispatch order

`MobileNativeActivity`'s default `plugins` becomes
`GeneratedPlugins.activePlugins + GeneratedAppPlugins.plugins`, computed
once per process. **libmobile's plugins come first** (core, then
features, in `codegen::PLUGINS` order), then the app's, **in the order of
the `Project::plugin` calls**. So an app plugin's `onCreate` runs after
the insets, intent and permission bridges are wired, and
`onActivityResult`/`onRequestPermissionsResult` reach libmobile's plugins
first; dispatch stops at the first plugin that returns `true`.

A subclass that overrides `plugins` keeps full control; its documented
form becomes `GeneratedPlugins.activePlugins + GeneratedAppPlugins.plugins + MyPlugin`.

### 3.3 Naming

- The class is given **fully qualified**, and must be a Kotlin `object`
  implementing `dev.highbay.libmobile.MobileActivityPlugin` (it is listed
  by name, as libmobile's are).
- At least two dot-separated segments; each an ASCII identifier
  (`[A-Za-z_][A-Za-z0-9_]*`) and not a Kotlin hard keyword.
- **Reserved:** the package `dev.highbay.libmobile` itself and every
  package libmobile ships Kotlin in (`dev.highbay.libmobile.<dir>` for each
  `codegen::PLUGINS` directory, and their sub-packages). An app's class
  there could collide with libmobile's staged files.
- **Recommended, not enforced:** the app's own package, under its
  application id (`dev.tmzt.shottoss.media.MediaStorePlugin`). It is not
  enforced because a crate shared by several apps may keep its plugin in
  one package for all of them.
- The JNI export for an `external fun` follows the JNI rules
  (`Java_<package with _ as _1>_<Class>_<method>`), in the app's cdylib.

### 3.4 Finding the Kotlin sources

`AppPlugin::sources(dir)` names a **source root** (a package-tree root, as
Gradle's `srcDir` takes), relative to the app crate's root
(`CARGO_MANIFEST_DIR`), or absolute, exactly as `extra_script` resolves
its path. It may be called more than once. The roots are referenced in
place, not copied: the generated app module adds each one, once, to
`android.sourceSets["main"]`'s `java` and `kotlin` directories, so every
file under the root is compiled (helpers next to the plugin included).

A plugin with no `sources` is allowed: its object then comes from a
dependency (an AAR listed with `dependency`, or an `extra_script`).

`Project::generate` prints `cargo:rerun-if-changed` for each root, so
adding or removing the plugin's file re-runs the checks below.

### 3.5 Contributions

As libmobile's own `Contributes`, built up one item per call:

| Call | Goes to |
| --- | --- |
| `permission(name)` | `<uses-permission>` in the generated manifest, once (merged with `Project::permission`'s) |
| `manifest(xml)` | directly inside `<manifest>`, before `<application>` (`<queries>`, `<uses-feature>`) |
| `application(xml)` | directly inside `<application>`, at its end (`<provider>`, `<receiver>`, `<meta-data>`) |
| `dependency(coordinate)` | `implementation` in the app module's `dependencies` |

Each list is deduplicated across the app's plugins in registration
order. They are rendered into the generated project, not into
`libmobile.gradle`, which belongs to libmobile's feature set and not to
one app.

### 3.6 Validation

Constant mistakes in the build script panic at the call, with a message
that starts `libmobile:` and names the value (the `url_scheme` pattern):

- `AppPlugin::new`: a class name that breaks 3.3's syntax or is in a
  reserved package;
- `permission`: empty, or characters other than `[A-Za-z0-9_.]`;
- `manifest` / `application`: not starting with `<` and ending with `>`
  after trimming;
- `dependency`: not `group:artifact:version` (3 or 4 non-empty parts, no
  whitespace or quotes);
- `Project::plugin`: a class already registered.

What depends on the filesystem is checked by `Project::generate`, which
returns an `io::Error` naming the path, before writing anything:

- a source root that does not exist or is not a directory;
- a plugin with sources whose `<root>/<package as dirs>/<Class>.kt` is in
  none of its roots;
- that file not declaring `object <Class>`.

### 3.7 The Kotlin surface an app plugin may use

Kept minimal and stable, covered by Rule 5 like the Rust API:

- `dev.highbay.libmobile.MobileActivityPlugin` and its hooks;
- `dev.highbay.libmobile.MobileNativeActivity` (the activity the hooks
  receive, and its `plugins` for subclasses);
- `GeneratedPlugins.activePlugins` and `GeneratedAppPlugins.plugins`, for
  a subclass that builds its own list.

Everything else in `dev.highbay.libmobile` (`NativeLib`, the `bridge`
objects, the feature plugins, `GeneratedPlugins`' flags) is internal and
may change in any release; Kotlin's `internal` cannot enforce that, since
everything compiles into one Gradle module, so the README says it. An app
plugin that needs one of libmobile's capabilities calls its own native
method and uses libmobile's Rust API from there.

The app's cdylib is registered with ART (`NativeLib.ensureLoaded`) before
any plugin's `onCreate`, so an app plugin's `external fun`s resolve from
its first hook on.

Activity and permission request codes `0x4000` to `0x7FFF` are libmobile's;
an app plugin uses codes outside that range.

### 3.8 Version

All of it is additive: `gradle::AppPlugin` is new, `Project::plugin` a
new method on a struct with private fields, the codegen additions new
items; `GradleProject`, `generated_plugins_kt` and `gradle_script`'s
signature do not change, and an app without plugins gets the same
generated project. The new source root in `libmobile.gradle` holds only
the empty default. **Patch: 0.5.5.**

## 4. API

```rust
// libmobile::gradle
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct AppPlugin { /* private */ }

impl AppPlugin {
    pub fn new(class: &str) -> Self;                       // panics (3.6)
    pub fn sources(self, dir: impl AsRef<Path>) -> Self;
    pub fn permission(self, name: &str) -> Self;           // panics (3.6)
    pub fn manifest(self, xml: &str) -> Self;              // panics (3.6)
    pub fn application(self, xml: &str) -> Self;           // panics (3.6)
    pub fn dependency(self, coordinate: &str) -> Self;     // panics (3.6)
    pub fn class(&self) -> &str;
}

impl Project {
    pub fn plugin(self, plugin: AppPlugin) -> Self;        // panics on a duplicate
}

// libmobile::codegen (std-only, host-tested)
pub const APP_PLUGINS_OBJECT: &str = "GeneratedAppPlugins";
pub const APP_PLUGINS_DIR: &str = "app-plugins";
pub const APP_PLUGINS_ROOT_PROPERTY: &str = "LIBMOBILE_APP_PLUGINS_ROOT";
pub fn generated_app_plugins_kt(classes: &[&str]) -> String;
pub fn check_app_plugin_class(class: &str) -> Result<(), String>;
```

`gradle_script` adds, after the staged root:

```groovy
def libmobileAppPlugins = project.findProperty('LIBMOBILE_APP_PLUGINS_ROOT') ?: '<OUT_DIR>/app-plugins'
```

as a second `java.srcDir`/`kotlin.srcDir`. The default root is the
`app-plugins` directory beside the staged `java` root.

The generated `app/build.gradle.kts`, with plugins, gains before
`apply(from = <libmobile.gradle>)`:

```kotlin
// The app's own plugins (Project::plugin): their sources, AARs and list.
extra["LIBMOBILE_APP_PLUGINS_ROOT"] = "<project>/app/libmobile-app-plugins"
android.sourceSets["main"].java.srcDir("<root>")
android.sourceSets["main"].kotlin.srcDir("<root>")
dependencies {
    add("implementation", "<coordinate>")
}
```

## 5. Steps

1. **Codegen and the default list.** `codegen`: the constants,
   `generated_app_plugins_kt`, `check_app_plugin_class` (syntax, keywords,
   reserved packages from `PLUGINS`' dirs), and the second root in
   `gradle_script`. `build.rs` writes the empty default into
   `OUT_DIR/app-plugins/`. `MobileNativeActivity`'s default list adds
   `GeneratedAppPlugins.plugins`, once per process; its doc and
   `MobileActivityPlugin`'s name the stable surface.
   **Done when:** host tests show the default and a two-plugin
   `GeneratedAppPlugins.kt`, the script's property fallback, and each
   class-name rule; an example with no app plugins still builds.
2. **`AppPlugin` and `Project::plugin`.** The builder and its panics; in
   `generate`, the filesystem checks, the `rerun-if-changed` lines, the
   generated `GeneratedAppPlugins.kt` (removed when there are none), the
   block in `app/build.gradle.kts`, and the manifest contributions.
   **Done when:** host tests render a project with an app plugin (the
   build script block, the list file, the manifest's permission,
   `<queries>` and `<application>` element, the dependency), show that a
   project without plugins is unchanged, and cover each validation error.
3. **Example.** The wgpu example registers
   `dev.highbay.libmobile.example.wgpu.ResumeLogPlugin` from
   `examples/wgpu/android/java`, which logs each `onResume` and calls an
   `external fun nativeResumed(count: Int)` implemented in the example's
   cdylib. **Done when:** `examples/build.sh wgpu` builds, `dexdump` of
   the APK shows `ResumeLogPlugin` and `GeneratedAppPlugins` listing it,
   and `llvm-nm -D` of the `.so` shows the native export.
4. **Release.** README (usage section and the stable Kotlin surface),
   0.5.5, `VERSIONS.md`, tag `v0.5.5`. **Done when:** the tag is on the
   version commit, and Rule 3.4's checks (fmt; clippy on the host and for
   `aarch64-linux-android` with no features and `--all-features`; tests)
   pass.
5. **libmorph.** libmorph and libmorph-build move to 0.5.5 in one commit
   (the recorded `links = "libmobile"` exception to Rule 3.1);
   libmorph-build's crate docs name `.plugin(AppPlugin::new(..))`; patch
   releases libmorph 0.10.1 and libmorph-build 0.5.5, since libmobile's
   bump is a patch (Rule 5.5 does not apply). **Done when:** libmorph's
   workspace builds and tests against 0.5.5, and
   `libmorph_build::gradle_project(..).plugin(..)` compiles in a test.
